# 思维链设计原则（Design Principles）

> 一套模板好不好用，取决于设计时是否守住了这些原则。本文讲"怎么设计"。

---

## 1. 先选方式

思维链塑形有三种方式，第一步先选方式：

| 需求 | 方式一：有结构 | 方式二：直接思考控制 | 方式三：软引导 |
|------|--------------|-------------------|--------------|
| 要不要标签 | 要（可解析、可检查） | 不要 | 不要 |
| 控制什么 | 标记结构 | 思考内容 / 顺序 / 角度 | 语言风格 |
| 泄漏风险 | 有（需防泄漏） | 无 | 无 |
| 稳定性 | 依赖环境（effort/客户端） | 稳定 | 稳定 |
| 适用场景 | 角色扮演、决策、有分歧任务 | **通用（最普适）** | 只调风格 |

选定方式一后，再选具体形式（说话人标记 or 路由式）。

---

## 2. 方式一：有结构（显式标记）

### 2a. 说话人标记

**核心：标记是"谁在说"，不是"流程步骤"。**

1. **说话人要有立场差异**：两个说话人必须真的对立（如"稳 vs 快"），否则没得辩，模型会敷衍。
2. **必须有 `[裁定]`**：一个拍板者决定谁赢，且**裁定结果直接决定输出**。
3. **标记用方括号 `[xx]`**：中性标记，不被当作 XML 标签。
4. **说话人名字短、有辨识度**：`[稳][快]` 比 `[方案A][方案B]` 更"像人"。
5. **不要给代码场景加字数限制**：字数限制只对"短对话"类有效，代码方案需要写清楚。

最小骨架：

```
[判断] 任务与难点。
[甲] 立场一。
[乙] 立场二。
[争执] 交锋。
[裁定] 谁赢及原因 → 直接决定输出。
```

### 2b. 路由式

**核心：入口分类决定走哪条流程。**

1. **入口 `[判断]` 要可判定**：分类规则明确、互斥、覆盖所有可能输入。
2. **每个分支是独立子流程**：数学走"步骤式"，决策走"辩论式"，创意走"发散→收敛"。
3. **路由结果直接决定后续**：分类错了整条流程就错，所以要**二次确认**。
4. **简单任务直接短路**：分类为"简单/直接指令"时不进入子流程，直接回答。

最小骨架：

```
[判断] 任务类型 + 复杂度。
  ├─ 简单 → 直接回答
  ├─ 数学 → [解题流程]
  ├─ 技术 → [评审流程]
  ├─ 决策 → [辩论流程]
  └─ 故障 → [诊断流程]
```

---

## 3. 方式二：直接思考控制（无标记，核心）

**核心：不管标签，直接命令模型"怎么想"，验证看思维链内容是否按命令执行。**

1. **命令要具体、可验证**：说"先列出 3 条风险"，不说"想想风险"——数量、角度、结论都要明确。
2. **控制"想什么"**：思考顺序（先→再→最后）、思考角度（正面+反面）、思考决策（必须给出结论）。
3. **不定义标记**：明确"用自然语言思考，不要写任何标记"。
4. **验证看内容**：检查思维链里是否列了 3 条风险、做了对比、给了结论，而不是检查有没有 `[xx]`。
5. **最省 tokens、无泄漏**：没有标签格式开销，也没有泄漏风险，是三种方式里最普适的。

最小骨架：

```
思考时必须按以下方式：
1. 先列出风险（至少 3 条）。
2. 再列出机会（至少 3 条）。
3. 对比后给出明确结论：做还是不做。
用自然语言思考，不要写任何标记。
```

---

## 4. 方式三：软引导（口癖 / 风格）

**核心：只塑造思考的语言风格，不控制具体步骤。**

1. **选一个口癖句式**：如 `we need to`，写进提示词正文各处。
2. **穿插第一人称情态动词**：`I'll` / `I can` / `I should` / `I will`。
3. **不定义标记、不规定步骤**：只靠句式塑造风格。
4. **适用**：通用场景，尤其不想约束具体思考路径时。

最小骨架：

```
你在思考时，请用第一人称、可执行的句式展开推理：
- 用 "we need to ..." 描述每一个具体动作。
- 穿插 I'll、I can、I need、I should。
- 短句、口语化，一步一句。
```

---

## 5. 通用原则（三种方式都要遵守）

1. **位置分离**：说"在 think 标签内完成、不要留在最终回答里"，不说"不要输出标记"。
2. **思考决定输出**：让思考的结论直接决定正文内容或形式。
3. **任务要有可辩/可控的东西**：没分歧的任务用简单提示词即可，硬套框架会敷衍或泄漏。
4. **环境要标注**：命中率依赖 `reasoning_effort` 和客户端环境。
5. **附范例**：给一段"思考长什么样"的完整示例。

---

## 6. 反模式（常见坑）

| 反模式 | 后果 |
|--------|------|
| 方式一里标记是流程步骤（`[第1轮]`）而非说话人 | 标记被省略，0 命中 |
| 说"不要输出标记" | 被理解为"全部隐藏"，连思考里也不写 |
| 描述思考标签的包裹/输出机制 | 标签污染正文 |
| 裁定不直接决定输出 | 模型跳过思考结构，命中率飘 |
| 代码模板加字数限制 | 方案写不清，无意义 |
| 没分歧的任务硬套辩论 | 敷衍或标记泄漏到正文 |
| 方式二的命令模糊（"想想风险"） | 模型自由发挥，思考不被控制 |
| 想要可解析标记却用方式二/三 | 标记不可解析，无法程序化检查 |
| 不标环境要求 | 换个客户端命中率暴跌，误判模板失效 |

---

## 7. 合格模板的自检清单

- [ ] 方式选对了（要标签用一，只控思考用二，只调风格用三）
- [ ] 方式一·说话人标记：标记是说话人，有 `[裁定]`，裁定直接决定输出
- [ ] 方式一·路由式：入口分类可判定、互斥、有二次确认，分支子流程独立
- [ ] 方式二：命令具体可验证（数量/角度/结论明确），不定义标记
- [ ] 方式三：只塑风格，不控步骤
- [ ] 方括号标记（方式一），不描述标签包裹机制
- [ ] 用"位置分离"表述，不写"不要输出标记"
- [ ] 附范例
- [ ] 标注环境要求（`reasoning_effort=max` / 客户端）
- [ ] 代码类模板无字数限制
